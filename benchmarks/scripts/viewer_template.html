About This Benchmark

This page reports how well 17 language models follow the DAAF (Data Analyst Augmentation Framework) orchestrator protocols when placed inside the real framework container. Each of the 1,700+ runs drops a model into a live DAAF session — hooks firing, skills discoverable, agents dispatchable — and scores its observable behavior: did it classify the request into the correct engagement mode and stop at the confirmation gate, did it load the reference files and skills the mode requires, did it dispatch the right subagent with a properly structured prompt. It measures behavioral conformance only. It does not measure answer quality, analytical capability, or general intelligence — a brilliant analyst model that skips confirmation gates scores poorly here, and a modest model that faithfully follows protocol scores well.

The benchmark phases

Each phase isolates one slice of orchestrator behavior. Later phases resume from golden checkpoints — truncated transcripts of known-good sessions — so every model starts from an identical mid-conversation state.

PhaseStarts fromWhat it tests
1 — Mode Classification
— cases		 A cold start: the model sees only the user's first request Does it pick the correct engagement mode, present a confirmation gate, and avoid executing anything prematurely?
2 — Post-Confirmation
— cases, one per engagement mode		 A checkpoint ending at the confirmation gate; the user says “Sounds good, let's proceed.” Does it load the mode reference files and skills it just committed to loading?
3a — Dispatch Compliance
— cases, 2 per agent type		 A checkpoint with Ad Hoc Collaboration mode fully initialized Does it dispatch the correct subagent type with a properly structured prompt (BASE_DIR, mode marker, task / context / instructions sections)?
3b — Subagent Behavior The subagent's own transcript, whenever a Phase 3 dispatch succeeds Did the dispatched agent behave according to its type — e.g., did a coding agent write a script and execute it through the audit-trail wrapper?
4 — Skill Routing
— cases		 The same initialized Ad Hoc checkpoint as Phase 3; the user asks a brainstorming question Does it follow the skills' own routing directives — FIRST reading the data-scientist hub's method-selection guidance, THEN loading the specific library skills the task calls for (e.g., pyfixest for fixed effects, geopandas for spatial work)?

Phase 3b is a sub-scoring of Phase 3 runs, not a separate batch: its criteria are derived from the agent type, and which criteria apply varies with the case, so its denominators differ from 3a's.

Phase 4 is reported as its own group throughout this page and does not enter the leaderboard composite or tier bands, which are pinned to the four core components (P1, P2, P3a, P3b).

How scoring works

Every run is graded against named criteria by deterministic scorers — transcript parsing with string and structural checks; no LLM judges anywhere in the loop. Each criterion is either hard (a structural must-pass, like agent_dispatched) or soft (a protocol detail, like whether the dispatch prompt carries a context section).

Three rates appear throughout this page, and they answer different questions:

  • Perfect (per run) — did all criteria pass on this run? This is the headline metric and the basis of the leaderboard composite.
  • Hard rate (per criterion) — across all of a model's runs, what fraction of its hard criteria passed?
  • Soft rate (per criterion) — the same, for soft criteria.

They diverge by design. Worked example: in a 12-run batch where 4 runs each fail exactly one soft criterion, Perfect drops to 67% (8/12 runs) while the hard rate stays at 100% and the soft rate stays around 96% — a model can look strong on criterion-level rates yet rarely deliver a fully clean run.

How runs were executed

Runs execute inside the real DAAF Docker container through the claude -p command line, with all framework hooks, permission rules, and skill discovery live — nothing is mocked. Phases 2–4 resume from golden checkpoints so every model starts at an identical protocol point, and each (phase, model, case) cell is repeated up to three times. Every batch archives to a timestamped, self-contained result set from which this page is generated.

Reading caveats
  • Timeouts are still graded. Runs that hit the wall-clock limit (some runs in this corpus) have zeroed cost, token, and turn counts, but their criteria are fully scored from the transcript produced before the cutoff — a timed-out run can be a perfect run. Cost and duration averages exclude these zeroed runs.
  • Denominators are uneven. Some (model, phase) cells have 2 reps instead of 3, so read every rate together with its n.
  • OpenRouter token counts are approximate. The Anthropic-compatible endpoint reports counts from Anthropic's tokenizer rather than each model's own, so computed costs for OpenRouter models are best-effort estimates.
  • Deterministic scorers have known false negatives. prompt_has_context_section is the canonical case: the scorer accepts seven heading variants, yet models often place genuine contextual content under headings outside that list and are marked down for it.
  • Fable 5's thinking blocks are encrypted, so reasoning-quality assessment for that model relies entirely on observable output.

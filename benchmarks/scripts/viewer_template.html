About This Benchmark

DAAF (the Data Analyst Augmentation Framework) is a free, open-source instructions framework that turns Claude Code into a structured research assistant: it routes each request into the right workflow, makes the assistant load the reference documents that define how the work should be done, hands work to specialist subagents with clear instructions, and requires methodological advice to be grounded in curated reference material rather than improvised from training data. A framework like that only works if the model inside it actually follows the structure — so this page measures exactly that.

Each of the 1,700+ runs drops one of 17 language models into a live DAAF session — hooks firing, skills discoverable, agents dispatchable, nothing mocked — and scores its observable behavior against the framework’s own rules. It measures behavioral conformance only: not answer quality, not analytical capability, not general intelligence. A brilliant analyst model that skips confirmation gates scores poorly here, and a modest model that faithfully follows protocol scores well. One honest confound to hold onto throughout: DAAF’s framework instructions were authored and tuned with Claude Opus 4.5/4.6 in mind, so part of any cross-model difference is prompting-style fit rather than capability.

Two bars run through every number on this page. Perfect is the high bar: did the model do everything exactly right on a run — every criterion passed, the protocol details included? It tells you how well, and how often, a model delivers a fully clean run, and it is the basis of the headline composite.

Critical-only is the lower but still valuable bar: if you are willing to accept some flaws in the details, will the model generally work through the system as intended? It counts only the must-pass criteria. The leaderboard’s metric toggle switches every rate, rank, and tier band between the two.

Glossary: ten terms this page leans on
  • Orchestrator — the main assistant in a DAAF session: it talks to the user, classifies requests, and coordinates everything else.
  • Subagent — a specialist assistant the orchestrator delegates work to (a data analyst, a code reviewer, a debugger), each with its own working rules.
  • Skill — a curated reference document the assistant can load on demand, injecting domain expertise (a statistics library's quirks, a data source's structure) at the right moment.
  • Engagement mode — one of DAAF's nine workflow types (a full analysis pipeline, onboarding a new dataset, a quick lookup, and so on); every user request must be routed into one.
  • Confirmation gate — the required pause where the assistant states its plan and waits for explicit user approval before doing anything.
  • Golden checkpoint — a truncated transcript of a known-good session; later phases resume from one, so every model starts at an identical mid-conversation point.
  • Case — one benchmark scenario: a specific prompt with defined expected behavior and scoring criteria.
  • Rep — one repetition of a case: the identical prompt run again, because a model can succeed on one attempt and fail on the next.
  • Composite — a model's headline score: the unweighted mean of its rates across the five phase components (P1, P2, P3a, P3b, P4).
  • Tier band — a grouping of models whose composites cluster together; a new tier starts wherever the ranking shows a sufficiently large gap.
The benchmark phases

Each phase isolates one slice of orchestrator behavior. Later phases resume from golden checkpoints — truncated transcripts of known-good sessions — so every model starts from an identical mid-conversation state.

— cases		 The same initialized Ad Hoc checkpoint as Phase 3; the user asks a brainstorming question The research-brainstorming dimension: models cannot be relied on to draw research methodology from training data, so a genuine research assistant must judiciously load domain expertise through skill reference files — FIRST the data-scientist hub's method-selection guidance, THEN the specific library skills the task calls for (e.g., pyfixest for fixed effects, geopandas for spatial work) — to ground what it does, says, and recommends in real research methodology. How scoring works

Every run is graded against named criteria by deterministic scorers — transcript parsing with string and structural checks; no LLM judges anywhere in the loop. Each criterion is either critical (a structural must-pass, like whether a subagent was dispatched at all — agent_dispatched) or normal (a protocol detail, like whether the dispatch prompt carries a context section). The two bars described above come straight from this split: Perfect demands every criterion pass, Critical-only demands every critical criterion pass. (Earlier versions of this page and the benchmark docs called these tiers “hard” and “soft”.)

Three rates appear throughout this page, and they answer different questions:

  • Perfect (per run) — did all criteria pass on this run? This is the high bar, the headline metric, and the basis of the leaderboard composite.
  • Critical rate (per criterion) — across all of a model's runs, what fraction of its critical criteria passed?
  • Normal rate (per criterion) — the same, for normal criteria.

They diverge by design. Worked example: in a 12-run batch where 4 runs each fail exactly one normal criterion, Perfect drops to 67% (8/12 runs) while the critical rate stays at 100% and the normal rate stays around 96% — a model can look strong on criterion-level rates yet rarely deliver a fully clean run.

How runs were executed

Runs execute inside the real DAAF Docker container through the claude -p command line, with all framework hooks, permission rules, and skill discovery live — nothing is mocked. Phases 2–4 resume from golden checkpoints so every model starts at an identical protocol point, and each (phase, model, case) cell is repeated up to three times. Every batch archives to a timestamped, self-contained result set from which this page is generated.

Reading caveats
  • This is one view under one orchestration system, not a model exam. DAAF's framework instructions were written and tuned with Claude Opus 4.5/4.6 as the working model, so part of any score difference between models is prompting-style fit rather than capability. Read these results as one particular view of how models behave under a very specific AI orchestration system — not as an absolute indicator of model quality.
  • Timeouts are still graded. Runs that hit the wall-clock limit (some runs in this corpus) have zeroed turn counts and a duration recorded at the cutoff limit, but their criteria are fully scored from the transcript produced before the cutoff — a timed-out run can be a perfect run.
  • Denominators are uneven. Some (model, phase) cells have 2 reps instead of 3, so read every rate together with its n.
  • Dollar figures are estimates at published list prices, not invoices. The harness logs token usage via the Anthropic-compatible endpoint, whose counts come from Anthropic's tokenizer rather than each OpenRouter model's own billing meter, so dollar costs derived from those counts were unreliable and were removed. Per-Mtok figures on this page are published list prices; the battery-cost comparisons in Costs Detail are relative multipliers (vs Opus 4.8) built from those list prices and each model's observed token mix — taken from provider billing data, not the harness's counts — on an everything-uncached basis (defined there).
  • Deterministic scorers have known false negatives. prompt_has_context_section is the canonical case: the scorer accepts seven heading variants, yet models often place genuine contextual content under headings outside that list and are marked down for it.
  • Fable 5's thinking blocks are encrypted, so reasoning-quality assessment for that model relies entirely on observable output.

Cost vs. Performance

Each point is one model: its published price in dollars per million tokens of text ($/Mtok — a million tokens is roughly 750,000 words) against the selected performance basis (composite, or any single phase group, P1–P4) under the selected metric (Perfect or Critical-only) — up and to the left is better. The price axis is logarithmic: each major gridline is 10× the previous one, which is the only way to fit models whose prices span more than a hundredfold onto one chart. The stepped line traces the efficiency frontier — the models no other model beats on both price and conformance at once; anything off the line is outperformed somewhere cheaper. The price-basis toggle also offers battery cost (× Opus 4.8) — the estimated relative cost to run the full benchmark battery once, expressed as a multiple of Opus 4.8, which folds each model’s observed token appetite into the price axis (defined, with its caveats, in Costs Detail). The per-Mtok bases are list rates, not measured benchmark spend. Shape and color mark the serving provider; hover any point for its exact figures.

Cases & Consistency

Two layers on the same repetition data. Because these models are probabilistic, each case is run multiple times — each rep is the identical prompt run again from the identical starting point. The agreement heatmaps show, for every case and model, how many of those reps were perfect runs (k/n in every cell) — split cells expose flaky cases and flaky models at a glance, and the All models margin gives each case's cross-model difficulty, hardest cases first. Costs Detail

The headline figure here is the estimated relative cost to run the full benchmark battery once — every probe in the suite, one repetition — computed for each model from its own observed token appetite at published list prices and expressed as a rough multiple of Opus 4.8 (= 1.0×). Two models at the same list price can differ in what a task actually costs, because one chews through more tokens to do the same work; these multipliers capture both the price tag and the appetite. The published per-million-token list prices follow as a secondary table below it (click any column header to sort; the Perfect Rate context column can be scoped to a single phase group via the toggle, the pricing columns never change with the scope).

Earlier versions of this page reported observed dollar spend computed from the harness’s per-run token counts. That tracking was removed: the harness logs token usage through an Anthropic-compatible endpoint whose counts come from Anthropic’s tokenizer rather than each model’s own billing meter, so token-derived dollar figures were unreliable. The battery estimates above avoid that trap by taking each OpenRouter model’s token mix from the provider’s own billing meter (via the billing-export reconciliation described above) and each Anthropic model’s from Anthropic’s usage logs — then pricing every token at published list rates. They are estimates built from list prices and observed token mixes, not a reading of an invoice for these exact runs.

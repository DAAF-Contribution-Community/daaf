## Core Principles - NON-NEGOTIABLE

These five principles must guide ALL data science work. They are not optional.

### Principle 1: Data Robustness First

**ALWAYS check data before operating on it.**

Before ANY analysis or transformation:
- Check shape, types, and memory usage
- Examine value distributions and ranges
- Identify and characterize missing values (count, percentage, pattern)
- Understand what uniquely identifies each row (granularity)
- Look for outliers and anomalies

Be VERBOSE about what you're checking and what you find. Never assume data is clean.

```python
# ALWAYS start with this pattern
print(f"Shape: {df.shape}")
print(f"Columns: {df.columns.to_list()}")
print(f"Types:\n{df.dtypes}")
print(f"Null counts:\n{df.null_count()}")
print(f"Sample:\n{df.sample(5)}")
```

This principle applies only when you are conducting actual data work. Do NOT conduct net new analyses or data inspections when tasked with compiling past work (e.g., analytic notebook creation), or synthesizing prior analyses into a report (e.g., final report writing).

### Principle 2: Documentation First

**ALWAYS understand or create data documentation.**

Before analysis:
- Seek data dictionaries, schemas, or documentation
- Understand where data comes from (provenance)
- Learn collection methods and their implications
- Identify known quality issues or caveats
- Clarify what each column means in business context

If documentation doesn't exist, CREATE IT as you learn about the data.

### Principle 3: Verify Every Operation

**NEVER assume a transformation worked correctly.**

For EVERY data operation:
- Check row counts before and after
- Examine random samples of affected rows
- Validate that expected changes occurred
- Confirm no unintended side effects
- Document what you checked and what you found

```python
# Before transformation
print(f"Before: {len(df)} rows, columns: {df.columns.to_list()}")
sample_before = df.filter(pl.col("id").is_in([1, 42, 100]))

# After transformation

sample_after = result.filter(pl.col("id").is_in([1, 42, 100]))
print(f"Sample comparison:\nBefore:\n{sample_before}\nAfter:\n{sample_after}")
```

### Principle 4: Thorough Code Documentation (ENFORCED)

In research workflows, follow the **Inline Audit Trail (IAT)** standard (see `agent_reference/INLINE_AUDIT_TRAIL.md`). The IAT standard is enforced during QA review — scripts with sparse documentation receive WARNING findings.

**Balance rigor with usefulness.**

Always consider:

## Essential Workflows

### New Data Workflow

When you receive new data, ALWAYS follow this sequence:

1. **Load and inspect** (do not transform yet)
   ```python
   # Load data
   df = pl.read_csv("data.csv")  # or scan_csv for lazy
   
   # Immediate inspection
   print(f"Shape: {df.shape}")
   print(f"Columns: {df.columns}")
   print(f"Types:\n{df.dtypes}")
   print(f"First 5 rows:\n{df.head()}")
   print(f"Last 5 rows:\n{df.tail()}")
   print(f"Random sample:\n{df.sample(5)}")
   ```

2. **Check data quality**
   ```python
   # Missing values
   print(f"Null counts:\n{df.null_count()}")
   print(f"Null percentages:\n{df.null_count() / len(df) * 100}")
   
   # Duplicates
   print(f"Duplicate rows: {len(df) - len(df.unique())}")
   
   # Unique values per column
   for col in df.columns:
       print(f"{col}: {df[col].n_unique()} unique values")
   ```

3. **Understand distributions**
   ```python
   # Numerical columns
   print(df.describe())
   
   # Categorical columns - value counts
   for col in df.select(pl.col(pl.String)).columns:
       print(f"\n{col}:\n{df[col].value_counts().head(10)}")
   ```

4. **Identify granularity**
   ```python
   # What uniquely identifies a row?
   # Test candidate keys
   candidate_keys = ["id", "user_id", ["user_id", "date"]]
   for key in candidate_keys:
       cols = [key] if isinstance(key, str) else key
       unique_count = df.select(cols).n_unique()
       print(f"{cols}: {unique_count} unique vs {len(df)} rows")
   ```

5. **Document findings** before proceeding

       .filter(pl.col("last_login") > cutoff_date)  # Remove inactive
       .group_by("user_id")
       .agg(pl.col("amount").sum().alias("total_spend"))
   )
   ```

   print(f"Sample before:\n{pre_sample.filter(pl.col('user_id').is_in(sample_ids))}")
   print(f"Sample after:\n{result.filter(pl.col('user_id').is_in(sample_ids))}")
   
   # Validate invariants where applicable
   # (e.g., sum should be preserved or explainably different)
   ```

## What is Federal Student Aid?

Federal Student Aid (FSA) is the office within the U.S. Department of Education that administers Title IV aid programs:

- **Title IV Programs**: Federal financial aid authorized under Title IV of the Higher Education Act (HEA)
- **Institutional Coverage**: All Title IV-eligible postsecondary institutions (approximately 5,500+ schools)
- **Data Types**: Aid disbursements, recipient counts, loan/grant volumes, financial responsibility metrics
- **Primary Identifier**: `unitid` (6-digit IPEDS institution ID)
- **Years Available**: 1999-2021 depending on dataset

## Common Pitfalls

| Pitfall | Issue | Solution |
|---------|-------|----------|
| Using string codes | Portal encodes categoricals as integers; original FSA docs may reference string labels | Always use integer codes (e.g., `grant_type == 1` not `"Pell"`) |

## CAVEATS

### 1. FSA Does NOT Provide Enrollment Denominators

This is the single most important caveat for computing Pell share. The FSA grants dataset provides:
- **Pell recipient count** (`grant_recipients_unitid` where `grant_type == 1`)
- **Pell disbursement amount** (`value_grants_disbursed_unitid` where `grant_type == 1`)

It does NOT provide total enrollment. To compute "share of students receiving Pell Grants," you must join to an external enrollment source. See the PATTERNS section for denominator recommendations.

### 2. Pell Is Undergraduate-Only

Pell Grants are restricted to undergraduate students. The Pell recipient count therefore reflects undergraduate Pell recipients only. The denominator for Pell share should be **undergraduate enrollment** (not total enrollment including graduate students). Using total enrollment would systematically understate Pell share at institutions with large graduate programs.

### 3. Year-Round Pell (Post-2017)

Beginning in 2017-18, students can receive up to 150% of their scheduled Pell award in a single award year (enabling summer enrollment). This may cause:
- Slight inflation in recipient counts if a student receives multiple disbursements coded as separate records
- Higher total disbursement amounts per student
- Impact is likely small for Pell share computation (since it affects counts, not the population denominator) but should be documented

### 4. Award Year Definition

FSA `year` represents the academic award year starting July 1 (e.g., `year == 2020` means the 2020-21 award year, July 1 2020 through June 30 2021). This differs from:
- IPEDS fall enrollment (typically October snapshot)
- IPEDS graduation rates (cohort-based, with specific cohort start year)
- IPEDS admissions (for a specific entering class)

When joining FSA to IPEDS, the `year` field may not perfectly align. Typically, FSA `year == 2019` (AY 2019-20) aligns with IPEDS fall 2019 enrollment data, but verify this alignment for the specific analysis.

### 5. Data Lag

FSA data in the Portal extends through 2021. If the analysis requires years beyond 2021, this source is insufficient. For graduation rate and admissions data from IPEDS that may extend to more recent years, there will be a gap where FSA Pell data is unavailable for the latest IPEDS years.

### 6. Allocation Flag Institutions

Some institutions have `allocation_flag == 1`, meaning their data was allocated across multiple unitids (e.g., multi-campus systems). For these institutions, the Pell recipient count at any single unitid may be an allocated portion rather than a directly reported figure. This could introduce noise.

### 7. Coverage: Title IV Participants Only

FSA data only includes institutions participating in Title IV programs. Institutions not participating (rare among degree-granting institutions, but more common among short-term certificate programs) will have no FSA record. When joining to IPEDS, some IPEDS institutions may not appear in FSA data.

### 8. Suppression Patterns

Missing data code `-3` indicates suppression due to small cell sizes. For Pell grants specifically, suppression is relatively uncommon because Pell is the most widely used federal grant program and most institutions have sufficient recipients to avoid suppression. However, very small institutions or those with very few Pell recipients may have suppressed values.

**Typical suppression rates for Pell in the grants dataset:** LOW — Pell is the highest-volume grant program. Suppression is more common for smaller programs (TEACH Grant, Iraq/Afghanistan Service Grant, Children of Fallen Heroes). The `-1` (not reported) code is more likely than `-3` for Pell, indicating that the institution simply did not report rather than that values were suppressed.

### 9. Cross-State Comparability

FSA data is nationally comparable for Pell share analysis. Pell Grant eligibility and award calculations are federally standardized (based on SAI/EFC, cost of attendance, and enrollment intensity). There are no state-level variations in how Pell is administered. However, state-level financial aid policies (state grants, tuition levels) affect which students enroll and where, indirectly affecting institutional Pell share.

## PITFALLS

### Critical Pitfall 1: Using Total Enrollment Instead of Undergraduate Enrollment as Pell Share Denominator

**Risk:** Systematically underestimating Pell share at research universities and graduate-heavy institutions.

**Detection:** After computing Pell share, check if research universities (R1/R2) have suspiciously low Pell shares compared to known benchmarks. A typical 4-year institution has 30-40% Pell share; if R1 universities show 10-15%, the denominator likely includes graduate students.

**Avoidance:** Always use undergraduate-specific enrollment from IPEDS as the denominator. Verify by checking that Pell share values are reasonable (typically 15-80% for most institutions).

### Critical Pitfall 2: Failing to Filter Out Sentinel Values (-1, -2, -3)

**Risk:** Including sentinel values in aggregations (sums, means) will produce incorrect results. A `-1` in `grant_recipients_unitid` is NOT "negative one recipient" — it means "not reported."

**Detection:** Check for negative values in recipient count and disbursement columns before any aggregation. Run `df.filter(pl.col("grant_recipients_unitid") < 0).shape` to see how many rows have sentinel values.

**Avoidance:** Always filter to `> 0` or explicitly exclude `-1, -2, -3` before computing sums, means, or ratios.

### Critical Pitfall 3: Year Misalignment Between FSA and IPEDS Graduation Rates

**Risk:** IPEDS graduation rates are cohort-based (e.g., `year == 2014` means the cohort that started in fall 2014, with 6-year graduation measured in 2020). FSA `year == 2020` means the 2020-21 award year. If the analysis aims to associate Pell share with graduation rates, the analyst must decide which FSA year to use — the cohort start year or the graduation measurement year.

**Detection:** Look for implausible or weak correlations that may stem from temporal misalignment.

**Avoidance:** For a selectivity/graduation rate analysis, the most defensible approach is to use FSA Pell data from approximately the same period as the graduation rate cohort's enrollment (e.g., for a cohort starting in 2014, use FSA year 2014 or nearby years). Alternatively, average Pell share across multiple years to smooth annual fluctuations.

### Critical Pitfall 4: Summing Across Aggregate and Detail Loan Types (Loans Dataset)

**Risk:** Not relevant to Pell share computation, but important if using loan data alongside grants. Loan type codes 3, 6, 9, and 14 are aggregate totals of their component types. Summing code 1 + code 2 + code 3 would double-count because code 3 = code 1 + code 2.

**Detection:** Check if aggregate loan totals appear suspiciously high.

**Avoidance:** Use either individual types (1,2,4,5,7,8) or aggregate types (3,6,9), never both.

### Pitfall 5: Ignoring the Allocation Flag

**Risk:** For institutions with `allocation_flag == 1`, the Pell recipient count at that unitid may be an allocated portion of a multi-campus system's total. This could result in understated or noise-affected Pell counts at specific campuses.

**Detection:** Check the prevalence of `allocation_flag == 1` in the data. If rare (<5% of institutions), the impact is minor.

**Avoidance:** Document the limitation. Optionally filter to `allocation_flag == 0` for a cleaner analysis, or keep all institutions and note that some counts are allocated.

### Pitfall 6: Using String Codes for Portal Integer-Encoded Variables

**Risk:** Filtering with `grant_type == "Pell"` or `grant_type == "1"` (string) will silently return zero rows because the Portal encodes all categoricals as integers.

**Detection:** If a filter returns unexpectedly zero rows, check whether integer vs. string encoding is the issue.

**Avoidance:** Always use integer codes: `pl.col("grant_type") == 1`.

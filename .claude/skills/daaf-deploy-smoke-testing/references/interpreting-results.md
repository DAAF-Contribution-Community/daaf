# Interpreting Deployment Smoke Results

Probe-by-probe interpretation for the DAAF deployment smoke suite: what each verdict means, which signals are expected mechanics rather than defects, route-conditional expectations, and how to route a real failure to its documented fix. Read this alongside a `report.md` from `scripts/deploy_smoke/reports/{timestamp}_{route}/`.

## Verdict Semantics

| Verdict | Meaning | Affects exit code? |
|---------|---------|--------------------|
| **PASS** | The probe's machinery worked as expected. | no |
| **FAIL** | A real defect for this route. Fix before trusting the deployment. | **yes** (nonzero) |
| **WARN** | Something worth a look, but not necessarily broken. Often expected on short headless runs (see below). | no |
| **SKIP** | Not applicable to the detected route (e.g. shim `/health` on a non-shim route). Correct behavior. | no |
| **INFO** | Informational context (e.g. the model-family/ceiling-hook posture), not a pass/fail signal. | no |

Only **FAIL** flips the overall verdict, matching the `run_all_smoke_tests.sh` contract. When triaging a report, read every FAIL first, then scan WARNs against the "expected mechanics" notes below before treating one as a defect.

The suite is **capability-structural**: Tier 1–2 probes check whether the machinery worked (did a subagent dispatch, did a script run, did a Skill load), *not* whether the model followed DAAF's protocols with high fidelity. Adherence quality is DAAFBench's job. A probe that PASSes confirms the plumbing is intact, not that the model behaves ideally.

> **Tier 0 limitation — ambient env only.** Tier 0 runs **once**, against the ambient (as-launched) environment, before any profile overlay is applied. Its route/env-coherence and context-window checks (T0.1–T0.4) therefore describe the base installation, **not** any `--profiles` overlay. A profile that, say, sets `ANTHROPIC_MODEL` to a GLM slug and declares its window via `CLAUDE_CODE_MAX_CONTEXT_TOKENS` is exercised only in that profile's Tier 1/2 runs — Tier 0 never re-validates per-profile overlays. Separately, before paid Tier 1/2 launches the runner repeats **only main-model coherence** for each actual child environment (including when Tier 0 is omitted). Known incompatibility blocks that profile, not compatible siblings; unresolved/WARN preserves ordinary exit behavior. When multi-profiling, read each profile's overlay in `profiles.yaml` directly to confirm its window/remap declarations; the Tier 0 verdict speaks to the ambient config alone.

## Tier 1 — One Live Round-Trip

A single cold-start `claude -p` call plus the plumbing checks around it. Two of these probes (T1.4, T1.5) often report **INFO** on short headless runs. That is expected mechanics, not an install defect, and knowing why prevents false alarms.

**Live-run health gate.** Before judging anything, the suite checks whether a real model actually answered. A `claude -p` run can exit cleanly while no model ran. With an unknown model slug, an exhausted spend cap, or an API error, the CLI writes a local assistant record: `message.model` is `<synthetic>`, `isApiErrorMessage` is `true`, and `error` is `"model_not_found"` (observed 2026-09-24). That record's error sentence then comes back as the "response". The gate fails the run if any of these hold:

- the CLI result has `is_error: true`, a `subtype` other than `"success"` (except `"error_max_turns"`, below), or a non-null `api_error_status`. Every `api_error_status` seen so far has been null, so treating a non-null value as an API failure is inferred, and the reason says so;
- the transcript **ends** on an API-error record: some assistant record has `isApiErrorMessage: true` or an angle-bracketed placeholder model, and no real-model assistant record follows the last such record;
- `modelUsage` names no real model;
- the run timed out or the CLI errored.

T1.1, T1.7 and every Tier 2 probe then FAIL with that reason. T1.5 and T1.6 SKIP, since there is no real session to judge.

Two conditions are a **WARN** instead, because a real model did answer. In both cases the probe still judges its own evidence, and a PASS becomes WARN with the reason appended as "Live-run warning: …". This applies to T1.1 and every Tier 2 probe.

- **A recovered transient error.** A mid-response provider error is written as the same kind of `<synthetic>` record (`error: "server_error"`, text "API Error: Server error mid-response. The response above may be incomplete."). The CLI then retries. The observed pattern is real record → error record → real record, in about 20 headless transcripts on the GPT lanes. The warning gives the number of error records and the first one's error and text, truncated. If no real record follows the **last** error record, the run ended on the error, and that is a FAIL.
- **A `--max-turns` stop.** CLI result `subtype: "error_max_turns"`. The run hit its turn limit before finishing, so a missing completion token or marker FAILs on the probe's own check, with the max-turns note attached. The exact shape of this result object (for example whether `is_error` is also true) has not been observed in this repo, so the gate accepts either value.

The suite therefore judges only what a headless run can positively show: the model cache must match the transcript model when present, and a hook injection counts only when it is real. Absence is reported as INFO with its reason, not as PASS or WARN.

## Tier 2 — Six-Probe Functional Battery

Each probe is a separate cold-start run. All checks are capability-structural and deliberately tolerant of stylistic/protocol variation. Each probe first applies the Tier 1 **live-run health gate**. A run where no real model answered (a transcript that ends on a `<synthetic>`/API-error stub, `is_error`, a non-`success` subtype, a non-null `api_error_status`, or an empty `modelUsage`) is a **FAIL** that names the reason, never a PASS or a vacuous SKIP. A recovered transient error, or a stop at `--max-turns` (subtype `error_max_turns`), is not a gate FAIL. The probe judges its own evidence, and a PASS becomes WARN with the reason (see the Tier 1 gate above).

Every Tier 2 run works inside its own **per-run, UUID-owned sandbox** — `scripts/deploy_smoke/_sandbox/run_<uuid>/`, created fresh at the start of the run and removed in a guaranteed cleanup path (scoped to exactly that directory — never a recursive wipe of `_sandbox/` and never a sibling). This is what makes the T2.1/T2.2 fixtures fresh *by construction*: a run directory left behind by a hard process kill carries a UUID no future run mints, so it is inert crash residue that cannot satisfy a later run. The two historical root-level fixtures (`_sandbox/t21_marker.txt`, `_sandbox/t22_probe.py`) predate this design and are non-authoritative; all of `_sandbox/` stays git-ignored.

| Probe | PASS means | FAIL/SKIP interpretation |
|-------|-----------|--------------------------|
| **T2.1 Subagent dispatch + search** | An `Agent`/`Task` tool_use occurred **and** the marker token came back in the orchestrator's response. | WARN = a dispatch happened and a subagent transcript exists, but the marker did not come back: dispatch works, relaying the result does not. FAIL = anything else (no dispatch, or a dispatch with no subagent transcript and no marker). On non-Claude routes, cross-check the ceiling-hook posture (T0.2) — a mis-set remap can block dispatch. |
| **T2.2 Coding agent write + execute** | `research-executor` wrote a script and ran it via `run_with_capture.sh`, and *this run's* execution left fresh captured evidence. PASS requires **all** of: this run's probe script exists; **exactly one** of the wrapper's three-line execution-log banner *frames* is present, where a frame is `# ` + **40 or more** `=` / `# EXECUTION LOG` / the same rule again (the wrapper writes 77 `=`); a `# Exit code: 0` record and a `# Capture: COMPLETE` record both appear **after** that banner; the wrapper's structural records `# Command: …`, `# --- STDOUT ---`, and `# --- STDERR ---` all appear after the banner **in that order** (fact `frame_records`); and this run's unique nonce appears **between** the `# --- STDOUT ---` and `# --- STDERR ---` markers (fact `nonce_in_stdout`) — the only region of the log carrying `# `-prefixed captured output. The nonce (not just the script's presence) is what ties the PASS to freshly captured output rather than source text; the rule-width floor and the record skeleton are what keep an agent from forging the evidence in the script source. | FAIL = any one of those is missing. A nonce that appears only in the script source *or* only outside the captured-STDOUT region, a stale banner from a prior run, a recorded nonzero exit, or a `Capture: INCOMPLETE` record (the wrapper's signal that the archived stdout may be truncated, exit 74) are each a **FAIL** — never a PASS-with-note. So are both banner-count failures, reported as `banner_count`: **0** = no qualifying frame — a bare `# EXECUTION LOG` line written into the source, *or* one wrapped in a token `# =` rule, is not a banner (the script never ran); **2+** = a forged frame stacked ahead of the real appended log, or a duplicated append (ambiguous evidence, so FAIL even if the records after the first frame look clean). The width floor matters because the wrapper **refuses to run** a script whose source already carries the marker: a source-forged frame is never joined by a real one, so `banner_count` stays at the passing value of 1 and the frame itself must be rejected on its shape. Confirms the file-first execution path and `enforce-file-first.sh` are intact *for this run*, not merely that a script file exists. |

The built-in `WebFetch` is NOT a pass signal: the `block-webfetch.sh` hook blocks it, so its presence means the agent used a disabled path, not working web access. | FAIL = no such call, or every web call errored or recorded no result (the evidence counts `web_calls`, `succeeded` and `errored_or_no_result`). Possible causes: a provider that does not surface WebSearch, a pre-rebuild image missing the fetch tool's dependencies, or a sandboxed network. |
| **T2.4 Skill loading** | A `Skill` call for **`polars`** (bare, or plugin-qualified `x:polars`) returned a non-error tool_result. Any Skill call is not enough, because the orchestrator skill loads first in most sessions. | FAIL = no successful `polars` Skill call; the evidence lists every skill that was called. Progressive disclosure may not be firing, or the model loaded the wrong skill. |
| **T2.5 Isolation-strip hook** | An `Agent`/`Task` tool_use asked for `isolation`, and `block-remote-isolation.sh`'s own hook attachment (its `command` names the hook) carries `updatedInput`. | **SKIP is tolerated**: if the model omitted or refused the `isolation` parameter, there is nothing to strip (not a FAIL). WARN = isolation was requested but that hook attachment is absent, though the dispatch did not hang. Another hook's `updatedInput` does not count. |
| **T2.6 Nested-dispatch prevention** | The dispatched subagent could not launch a nested subagent. The verdict reads **only the subagent transcripts**, never the main transcript's content (the main transcript is read only to link each subagent transcript to its top-level call), where the orchestrator skill's prose about nested subagents once passed as a "denial". There are two PASS layers. **(a) Harness layer:** the subagent attempted nothing, and neither its recorded tool list (the `prompt_snapshot` attachment's `tools`) nor its deferred tool names (`deferred_tools_delta` attachments' `addedNames` minus `removedNames`, when present) include `Agent` or `Task`. Names match exactly, so the deferred `TaskOutput`/`TaskStop` tools don't count. On 2.1.281 the attachment is sometimes absent and sometimes present. The 17:29 live run's subagent on 2026-09-24 listed 22 deferred names, including `TaskStop` but not `Agent` or `Task`. With `CLAUDE_CODE_MAX_SUBAGENT_SPAWN_DEPTH=1` in `settings.json` `env`, Claude Code withholds both tools from every subagent (observed 2.1.261 and 2.1.281; the Claude Code changelog says only that the setting "disable[s] nesting"). The detail then reads: "Nested dispatch unavailable at spawn depth 1 (harness layer): the subagent's tool list (including any deferred tool names) has no Agent or Task tool, so it could not attempt one. Hook backstop (block-nested-dispatch.sh) not exercised." This is the expected result today. The harness layer also PASSes when the subagent **did** try a nested `Agent`/`Task` call while the tool was absent, and every such attempt got an error tool_result. The live 2026-09-24 run (session b5524e7f) showed this: the subagent called `Agent` anyway and got `<tool_use_error>Error: No such tool available: Agent. Agent is disabled for this session, in subagents as well as here.</tool_use_error>`. The detail then reads: "Nested dispatch rejected at spawn depth 1 (harness layer): the subagent's tool list (including any deferred tool names) has no Agent or Task tool, and each nested Agent/Task attempt got an error result because the tool was absent. Hook backstop (block-nested-dispatch.sh) not exercised." That wording is used only when every error text contains "No such tool available". Any other error text gets the neutral form: "Nested dispatch rejected at spawn depth 1 (harness layer): every nested Agent/Task attempt returned an error while Agent/Task was absent from the subagent's tool list (including any deferred tool names). Hook backstop (block-nested-dispatch.sh) not exercised." Tool absence counts only when **every** subagent transcript recorded its tool list; if any list is unrecorded, availability is unknown and an attempt grades WARN. **(b) Hook layer:** the subagent attempted an `Agent`/`Task` call and its transcript holds a real deny record. That is either an `is_error` tool_result (observed on earlier pins) or a hook attachment carrying `block-nested-dispatch.sh`'s text "may not launch nested subagents" (inferred shape, not yet observed live). At depth 1, `block-nested-dispatch.sh` is a backstop for when the limit is lifted or the harness regresses; its deterministic coverage is `tests/bash/block_nested_dispatch.bats` in Tier D. | **FAIL** = a nested dispatch actually ran. Three signals show it. (1) A subagent's own `Agent`/`Task` call got a non-error tool_result, wherever the child's transcript landed. (2) A subagent transcript links to no top-level `Agent`/`Task` call in the main transcript. Each transcript is linked to its parent by its `agentId`, which equals the parent result's `toolUseResult.agentId`, or by its opening prompt, which equals the parent's `input.prompt`. The prompt match was checked on stored transcripts: 10/10 subagents of one session, plus a terminated-early subagent and the 2.1.281 live one. (3) As a backstop for transcripts with no identity, there are more subagent transcripts than top-level calls. Errored top-level calls stay in the count. An "Agent terminated early due to an API error" result **did** start a subagent, and that subagent left a transcript; its result has no `agentId`, so its transcript links by prompt. A retry after such a failure (two calls, two transcripts) is therefore not read as nesting. The evidence records `top_level_dispatches`, `top_level_errored`, `linked_subagents`, `unlinked_subagents`, `unlinkable_subagents`, `retried_dispatch`, `nested_calls`, `nested_errored`, `nested_succeeded` and `nested_error_text`. If the main transcript is missing, nothing can be linked, and the check assumes one outer dispatch. Linkage knows only the main transcript's `Agent`/`Task` calls. A subagent started any other way inside the T2.6 session therefore reads as unlinked, and so as nesting (FAIL), although nothing nested. Examples are a slash-command review such as `/code-review` and a forked skill. Future probe changes must not launch such subagents inside the T2.6 session. On a FAIL, check that `CLAUDE_CODE_MAX_SUBAGENT_SPAWN_DEPTH=1` is still in `settings.json` `env`, and that the hook sits first in *both* the `Task` and `Agent` matcher chains and still receives the `agent_id`/`agent_type` fields it keys on. **WARN** = a nested attempt with no spawn and no deny record that is not the harness rejection above, e.g. the tool was available, or an attempt has no recorded result (inconclusive). **INFO** = no attempt and no recorded tool list, so only the model's own report is available, which is not evidence. **SKIP** = no subagent was dispatched (see T2.1), or the subagent had `Agent`/`Task` (in its tool list or as a deferred tool) but ignored the instruction. |

## Tier D — Deterministic Battery (opt-in, zero API cost)

Opt-in via `--tiers D` (with `--include-r-smoke` for TD.6). Every probe shells a repo test entry point and reports its exit code — no LLM, no cost. A missing tool is a **SKIP**, not a FAIL, so running Tier D outside the `DAAF_DEV=1` image degrades gracefully rather than failing spuriously.

**The harness self-tests itself first.** TD.0 discovers `tests/python/test_deploy_smoke*.py` *before* the broader batteries. This includes the existing harness contracts plus shared main-model preflight. These are provider-free contract tests, not live provider acceptance. For agent execution, use a fresh flat audited launcher with `unittest.defaultTestLoader.discover('/daaf/tests/python', pattern='test_deploy_smoke*.py')`, `sys.dont_write_bytecode=True`, and an assertion on `TextTestRunner(...).run(suite).wasSuccessful()`, executed through `run_with_capture.sh`.

**Deterministic environment isolation.** All Tier D subprocesses run under a sanitized copy of the live environment with exactly two variables stripped — `CLAUDE_CODE_MAX_CONTEXT_TOKENS` and `DAAF_BRANCH` — because a fully-configured live install legitimately exports both, and both steer default-window / default-branch fixtures onto the live session's values. This is defense-in-depth *atop* each battery's own fixture isolation (bats `setup()` unset, Pester `BeforeEach` removal), **not** `env -i`: `PATH`, `HOME`, route credentials, and the developer toolchain are all preserved so the batteries can still find their interpreters. TD.0's evidence records which variables were actually removed.

**Two-level evidence policy.** On a **PASS**, a probe keeps only a concise final excerpt (the last several lines) in the report. On a **FAIL or timeout**, the report quotes a bounded head-and-tail excerpt (so both the earliest failure names and the final summary stay visible) *and* the COMPLETE scrubbed output is persisted to `evidence/tier_d/{probe_id}.log`, referenced from the probe's evidence. All captured output is scrubbed for secret env values before it is quoted or persisted.

| Probe | PASS means | FAIL/SKIP interpretation |
|-------|-----------|--------------------------|
| **TD.0 harness self-test** | The deploy-smoke suite's provider-free `test_deploy_smoke*.py` modules pass — the harness's env sanitization, evidence capture, output routing, Tier 2 cleanup, and T2.2 freshness logic are all intact. Runs first so the rest of Tier D is trustworthy. | FAIL = a harness regression: fix the harness before trusting any other Tier D verdict. SKIP is not expected (it only needs stdlib `python3`); a FAIL here means the suite's own contracts broke. |
| **TD.1 bats tests/bash** | `bats tests/bash/` exits 0 (all Bash unit tests pass). | FAIL = a Bash test failed. SKIP = `bats` not installed (needs the `DAAF_DEV=1` image). |
| **TD.2 Pester tests/powershell** | `Invoke-Pester -Path tests/powershell -CI` exits 0 **and** its NUnit `testResults.xml` is present in the report at `evidence/tier_d/testResults.xml`. Pester runs with its working directory set to that evidence dir, so the XML lands report-local rather than at the repository root (`/daaf/testResults.xml` is never created). | FAIL = a PowerShell test failed, **or** Pester exited 0 but the report-local `testResults.xml` is missing (an artifact-routing failure — a zero exit with no XML is a TD.2 FAIL by contract, not a PASS). SKIP = `pwsh` not installed (dev image only). |
| **TD.3 daaf-conventions lint** | `tests/lint/check-daaf-conventions.sh` exits 0. | FAIL = a convention violation. Read the tail evidence for the offending file. |
| **TD.4 safety-hook tests** | `scripts/test_safety_hooks.sh` exits 0 (the `bash-safety.sh` battery passes). | FAIL = a safety-hook regression — investigate before trusting the deployment's guardrails. |
| **TD.5 single-command hook tests** | `scripts/test_enforce_single_command.sh` exits 0. | FAIL = an `enforce-single-command.sh` regression. |
| **TD.6 R/Python skill smoke suite** | (opt-in) log-stripped copies of `scripts/smoke_tests/smoke_*` run clean via `SMOKE_DIR`. | FAIL = a library smoke failed. **SKIP by default** — pass `--include-r-smoke` to enable (it is slow). Mirrors the CI staging pattern; runs under `scripts/scratch/smoke_live/`, never `/tmp`. |

## Route-Conditional Expectations and Known Failure Modes

Each route has a distinct configuration surface. Below: what Tier 0 expects for the route, and the known failure modes (with their documented fixes) that a live-tier FAIL most likely maps to.

### Route 1 — anthropic-subscription (native, no shim)

- **Expected:** No `DAAF_PROVIDER_SHIM`, no OpenRouter base URL. The session model resolves from `ANTHROPIC_MODEL` if set, else a saved `/model` choice, else the soft default `ANTHROPIC_DEFAULT_MODEL` that `settings.json` ships (`opus`, Claude Code's built-in Opus when unmapped). A Claude Enterprise organization default, if set, is not modeled. T0.3 records both start selectors; `ANTHROPIC_MODEL` is normally `<unset>`. `enforce-model-ceiling.sh` actively **ranks** subagent dispatches (haiku < sonnet < opus < fable). T0.2 should report family `claude`, `remap_active=false`.
- **Auth:** Interactive OAuth or `CLAUDE_CODE_OAUTH_TOKEN`. Tier 0 cannot verify interactive OAuth without an LLM call, so a genuine auth problem surfaces at **T1.1** (round-trip fails).
- **Known failure mode:** `ANTHROPIC_BASE_URL` unexpectedly set while the route detects as native — T0.3 flags it. Unset it for the native route.

### Route 2 — openrouter

- **Expected:** `ANTHROPIC_BASE_URL` ends with `openrouter.ai/api`; `ANTHROPIC_AUTH_TOKEN` set (your OpenRouter key, Bearer auth); `ANTHROPIC_API_KEY` **present-and-empty** (`ANTHROPIC_API_KEY=`) so the `X-Api-Key` header does not override Bearer auth. For non-Claude models, map all four tier aliases: the `ANTHROPIC_DEFAULT_OPUS_MODEL`/`SONNET_MODEL` remap keeps subagents pure and makes the ceiling hook **stand down**; `ANTHROPIC_DEFAULT_HAIKU_MODEL` carries Claude Code's housekeeping calls (naming and summarizing the session). Left unmapped, Claude Code has sent these as Claude Haiku requests that the route rejects (July 2026 shim logs); Claude Code's current docs say they run on the main, pricier model. `ANTHROPIC_DEFAULT_FABLE_MODEL` covers the `fable` alias. T0.4 checks every mapped slot's window. `CLAUDE_CODE_SUBAGENT_MODEL` alone does not reroute DAAF agents (a fallback only since Claude Code 2.1.251; `CLAUDE_CODE_SUBAGENT_MODEL_FORCE=1` forces it). `CLAUDE_CODE_MAX_CONTEXT_TOKENS` declares the real window.
- **Known failure modes (documented in `user_reference/01_installation_and_quickstart.md` § "Setup Troubleshooting", anchor `#setup-troubleshooting`):**
  - *"model not found" / auth errors* — three causes: wrong base-URL suffix, `ANTHROPIC_API_KEY` unset vs. empty, or a stale login needing `/logout`. T0.3 catches the base-URL and empty-key cases directly.
  - *`-pro` GPT slugs* — the July 2026 hard "Prompt is too long" wall (~200k reported tokens) did not reproduce in the 2026-09-29 retest (more than 930k reported tokens accepted; `research/2026-09-29_FrameworkDev_OpenRouterDottedModelNames/preliminary_notes/2026-09-29_openrouter-pro-retest.md`). A `-pro` "Prompt is too long" at low utilization is therefore no longer an expected known cause; check the window declaration (T0.4) first. The ~3–4x inflated token accounting persists, so `-pro` runs cost several times more and DAAF's context warnings fire earlier in real content terms (`01_installation_and_quickstart.md` § "GPT (OpenAI) models via OpenRouter (Option C, extended)", anchor `#gpt-openai-models-via-openrouter-option-c-extended`). Prefer a standard flagship slug for cost reasons.
  - *Ceiling-hook DENY on a non-Claude session* — if a non-Claude family is configured **without** an OPUS/SONNET remap, a Claude-tier subagent request is denied with remap guidance (`enforce-model-ceiling.sh` rule f). A per-dispatch `model` cannot fix it (the parameter accepts only Claude aliases); set the `ANTHROPIC_DEFAULT_*` remap vars for all four tiers. T0.2's INFO posture is the early warning. `CLAUDE_CODE_SUBAGENT_MODEL` alone no longer stands the hook down, and the deny message names the four `ANTHROPIC_DEFAULT_*_MODEL` settings, not that variable (hook updated 2026-10-12; an older installed hook still stands down for it, and T0.2 says when that hook is the one installed).
  - *Context under-reporting* — a GPT/non-`[1m]` slug without a window declaration → T0.4 FAIL.

### Routes 3 & 4 — shim (chatgpt-subscription, openai-api)

- **Expected:** `DAAF_PROVIDER_SHIM=openai`; `ANTHROPIC_BASE_URL` → `http://127.0.0.1:4141`; `ANTHROPIC_AUTH_TOKEN=daaf-shim-local`. Route 3 additionally needs `SHIM_BACKEND_MODE=chatgpt` and `CODEX_HOME` (holds `auth.json`); Route 4 needs `OPENAI_API_KEY` or `SHIM_BACKEND_API_KEY`. T0.8 shim `/health` must report the matching `backend_mode`.
- **Daemon state is not per-run overridable.** `SHIM_SANITIZE_TOOLS` and `backend_mode` are fixed at shim startup; `--profiles` overlays reach only the CLI session, so the runner WARNs if `--profiles` is used on a shim route. Verify daemon state read-only via T0.8.
- **Known failure modes:**
  - *Route 3 auth* — `codex_home_present=false` or T0.9 FAIL → `auth.json` missing/unreadable; run `codex login --device-auth`. Token refresh is JWT-`exp`-based and lazy; a genuinely expired, un-refreshable token surfaces at T1.1.
  - *GPT tool-call quirks* — `isolation`-fill hangs and empty `Read.pages` are handled by the shim's `_sanitize_tools` (default on, Routes 3–4) and, for `isolation`, by `block-remote-isolation.sh` at the hook layer. T2.5 exercises the hook-layer strip. For DAAFBench raw-model runs `SHIM_SANITIZE_TOOLS=0` is required — but that is a benchmark concern, not a deployment-health one.
  - *Route 4 instant 429* — an unfunded OpenAI API key returns 429 immediately (distinct from a ChatGPT subscription); surfaces at T1.1. Fund the API account or switch to the chatgpt route (`07_faq_technical.md` § "Q: My GPT session fails instantly with 429 errors on every request (Option F)", anchor `#q-my-gpt-session-fails-instantly-with-429-errors-on-every-request-option-f`).
  - *ChatGPT lane is an unofficial dev lane* — explicitly flagged as not OpenAI-sanctioned and liable to break (`01_installation_and_quickstart.md` § "Option F, alternate lane: ChatGPT subscription (Codex backend)", anchor `#option-f-alternate-lane-chatgpt-subscription-codex-backend`); a sudden T1.1 failure here may be upstream, not a local misconfig.

## Auto mode

Tiers 1–2 use `bypassPermissions`, so they never exercise Auto mode's classifier; check it with the single plain session in SKILL.md § Checking Auto Mode.

- **Working:** allowed actions run with **no permission prompt**. That is the point of Auto mode, so no pop-ups is the expected result. The status bar shows "auto mode on". Explicit ask rules (for example DAAF's `git push`) still prompt.
- **Denied:** Claude Code shows a notification, and the action appears in `/permissions` under *Recently denied*. Three denials in a row, or 20 in total, pause Auto mode and bring prompts back.
- **Classifier failure:** a message saying Auto mode "cannot determine the safety" of an action, with no *Recently denied* entry.
- **On shim routes:**
  - Claude Code cannot use Anthropic's server-side review (the `safeguards` pass-through), because the shim's upstream is OpenAI. It falls back to its own classifier requests, which go through the shim to the GPT model. In `shim.log`, a request line containing `stream=n msgs=<N> tools=0` is likely a classifier request. Treat that as a heuristic: other non-streaming, tool-less housekeeping calls share the pattern.
  - Claude Code announces that fallback with a notice that "this session isn't eligible" for the new classifier billing. On the pinned Claude Code version (2.1.281) the notice is harmless. Set `CLAUDE_CODE_AUTO_MODE_SERVER=0` (see the env template) to skip the server request and the notice.
  - After the first reply, `/status` shows "Auto mode server: Disabled". That is expected on these routes.
- **Upgrade gate:** a third party (LiteLLM, October 2026) reports that Anthropic told them Claude Code releases after 2026-10-23 support only server-side Auto mode, which is unavailable behind a gateway that doesn't support it; the shim never can. Anthropic's docs do not say so yet. If it holds, Auto mode stops working on GPT routes after such an update, and `CLAUDE_CODE_AUTO_MODE_SERVER=0` will not restore it. Before bumping the pinned Claude Code version (2.1.281), confirm that Auto mode still works on a shim route.

## Where Evidence Lands (for manual follow-up)

When a probe FAILs and the report evidence is not enough, these live locations carry more detail:

| Signal | Location |
|--------|----------|
| Shim health/config | `curl http://127.0.0.1:4141/health` → `backend_mode`, `codex_home_present`, `sanitize_tools`, `reasoning_effort`, `version` |
| Shim structured logs | `scripts/provider_shim/logs/shim.log` (credential-scrubbed) |

| Context-window cache | `/tmp/claude-ctx-window-{session}`, `/tmp/claude-or-models-{session}` (OpenRouter models cache) |
| Ceiling-hook stand-down/deny reasons | stderr of `enforce-model-ceiling.sh` and its `permissionDecisionReason` JSON |
| Report artifacts | `scripts/deploy_smoke/reports/{timestamp}_{route}/report.md`, `report.json`, `evidence/` (`shim_health.json`, `env_fingerprint.json`, `t07_statusline_cache/`, `t16_statusline_cache/`) |
